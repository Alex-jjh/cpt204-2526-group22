The Problem

A municipality has 1000 candidate inspection points connected by 2600 road segments. The inspection team has limited capacity and needs to answer two questions:

① Which 10 to inspect first?

Each location has a priority_score. Sort all candidates by priority (descending), then ID (ascending), and pick the top 10.

→ Task A: Bubble vs Quick vs Merge

② What's the cheapest route?

Given a start and end (and optional waypoints), find the shortest weighted path through the road graph.

→ Task B: Dijkstra over an adjacency list

Task A — Three sorts, three datasets

Bubble Sort

Adjacent compare-and-swap. Liang's early-exit flag: stop the moment a pass does no swaps.

best O(n) · avg O(n²)

Quick Sort

Lomuto partition with median-of-three pivot to dodge the O(n²) worst case on sorted input.

avg O(n log n)

Merge Sort

Top-down divide-and-conquer. Stable in all cases; trades O(n) extra space for predictable speed.

always O(n log n)

The three datasets are not interchangeable — each was crafted to expose a different algorithmic strength:

DatasetShapeHypothesis
Anearly sortedBubble's early-exit should win
BrandomQuick should dominate (cache-friendly)
Cmany tiesMerge's stability matters here

Methodology safeguards (per tutor's brief): 1 untimed warm-up to absorb JIT compilation · 3 timed runs · System.nanoTime() for sub-millisecond precision · fresh copy of the input list per run so in-place sorters don't see pre-sorted data.

Look at Case 3 carefully

The path retraces: … → L0106 → L0105 → L0106 → L0107 → …

This is the local-vs-global optimality evidence. We compose two Dijkstra calls (start → waypoint, waypoint → end). Each leg is locally optimal, but the concatenation can backtrack — because Dijkstra knows nothing about the other leg's geometry. A correct globally-optimal solver for k waypoints is the k-shortest-paths / TSP-with-waypoints variant; out of scope here, but discussed in §2.4 of the report.

Why Dijkstra + heap, not adjacency matrix

ApproachTimeSpaceFor V=1000, E=2600
Textbook Dijkstra (matrix scan)O(V²)O(V²)~10⁶ ops · 1 MB matrix
Floyd-Warshall (all pairs)O(V³)O(V²)~10⁹ ops
Ours: PQ-Dijkstra + adjacency listO((V+E) log V)O(V+E)~36 000 ops

Sparsity matters. Our graph has 2600 edges out of a possible ~500 000 — that's 0.5 % density. An adjacency matrix would be 192× wasteful in space, and the dense scan in textbook Dijkstra would touch 1000 cells per node even when only ~5 are real neighbours.

Alternatives we considered (§2.5 of report)

  • BFS — only correct for unweighted graphs · ours has weights, ruled out
  • A* — needs a geometric heuristic · we have no coordinates
  • Bellman-Ford — handles negative edges · we don't need that, and it's O(VE) = 26× slower

Task C — OOP design

Five packages
